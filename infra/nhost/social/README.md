The new `guild-commons-v1.sql` and `guild-commons-metadata.json` are
**not applied by this repository change**. Before an authorized migration,
verify the actual Nhost source, currently installed `social_week` function,
Auth deletion trigger, Hasura permissions and account role; take a definition
backup. Apply the SQL as the existing source role only after a disposable
PostgreSQL test confirms the exact current schema, including prior member-invite
upgrades. Track only the additive `guild_commons_v1` mutation and give the
`user` role function permission. The existing `response` return type is
reused; do not re-track it or reapply `metadata.json` in a live project.

This API uses the same account/membership serialization lock as `social_week`.
Only current members may read Guild notes and profile; each current member may
post one unexpired note, with at most three per Guild; the author may edit,
withdraw or resolve their own help note, and the earliest remaining member may
remove a note. A confirmed administrator handover changes the member order (the upgrade
alters its identity column from GENERATED ALWAYS to GENERATED BY DEFAULT),
which also changes administrator identity for the old RPC, and invalidates
any active invite code. Confirm this identity-column change and interaction
with all existing Guild triggers in disposable PostgreSQL before activation. There is no Guild XP, automatic learning-data sharing,
notifications, public message history or presence tracking in v1.

For a live rollout, verify A/B in one Guild, C in another, anonymous, stale
membership, simultaneous final-slot posts, edited/removed notes, Unicode limits,
Auth delete cascade, admin handover and outgoing-admin invite invalidation.
Check the actual Hasura JWT role and that the private tables remain untracked.
The client requests Commons only when a member explicitly opens it, and the
UI is disabled by default. Set `VITE_PROGRESSPAL_GUILD_COMMONS=true` only
after the separately authorized Nhost contract and metadata are installed and
verified. If the function is absent, the original Guild remains usable.
Expired notes are hidden after seven days and purged on the next authenticated
Commons operation; a dormant Guild's expired rows can remain in storage until
a separately approved housekeeping operation or Guild deletion. Do not call this
an unconditional seven-day physical retention guarantee.

The disposable contract probe applies `up.sql`, `rename-guild.sql`,
`member-invites.sql` and `guild-commons-v1.sql` to an in-memory PGlite and
checks the cases above except true concurrency (PGlite has one connection;
the final-slot race relies on the shared advisory lock):
`node infra/nhost/social/probe-guild-commons.mjs <pglite/dist/index.js>`.
The owner-run activation checklist is in `docs/guild-commons-delivery-plan.md`.

`probe-guild-commons-postgres.mjs` runs the same SQL on a **disposable local**
PostgreSQL (it refuses another host or a database that already has an `auth`
or `progresspal_social` schema, and drops what it creates). It proves the
shared advisory lock serializes concurrent connections, that a race for the
final slot and a two-device post each store one note, and, where pg_cron is
installed, the cleanup job below:
`node infra/nhost/social/probe-guild-commons-postgres.mjs <pg/lib/index.js> <local-database-url>`.

### Expired-note cleanup (pg_cron)

`guild-commons-cleanup.sql` registers one daily job,
`progresspal-guild-notes-purge` at 03:45 in `cron.timezone`, that runs
`DELETE FROM progresspal_social.guild_notes WHERE expires_at < now()` with the
database server's time, so a note is physically deleted at most 24 hours after
it expires. It first checks that pg_cron is installed, that the table exists
and that the current role may delete from it; `cron.schedule` replaces a job of
the same name, so applying it twice keeps one job. It does not touch other
jobs such as `progresspal-feedback-purge`. Apply it as the role that owns the
table, after `guild-commons-v1.sql`. It removes database rows only; provider
backups keep their own retention.

Verify after applying (read-only):

```sql
SELECT jobid, jobname, schedule, command, username, active
FROM cron.job WHERE jobname = 'progresspal-guild-notes-purge';
-- after 03:45 the next day:
SELECT status, return_message, start_time FROM cron.job_run_details
WHERE jobid = (SELECT jobid FROM cron.job
               WHERE jobname = 'progresspal-guild-notes-purge')
ORDER BY start_time DESC LIMIT 5;
```

`username` is the role the job runs as; a run's `status` should be
`succeeded` and `return_message` `DELETE <n>`. Unschedule safely with
`SELECT cron.unschedule('progresspal-guild-notes-purge');`, which stops the
job and keeps the notes.

Rollback should remove the Hasura function permission and tracking to disable
access, preserving live Guild records and `social_week`. Destructive table or
column rollback requires separate retention/deletion authorization.

This delta targets the existing Nhost PostgreSQL source and Hasura GraphQL API.
It requires PostgreSQL with built-in `gen_random_uuid()` and `sha256(bytea)`,
`auth.users(id uuid)`, and the authenticated Hasura role `user` on a read-committed source. Verify the
actual source name, role claims and source-role privileges, including permission
to create a trigger on `auth.users`, on the intended environment before use.
Use the source's database role to apply the SQL so the invoker RPC can access
its own tables and verify the account. The migration has no backup dependency.

The three data tables are private. The one tracked response table is permanently
empty, and the one tracked mutation uses Hasura's injected `hasura_session`
argument. Only the `user` role has metadata permissions. The mutation takes an
action and bounded JSON input. Every read/write is relative to the account in
the injected session. A share, leave or invite action also checks the caller's
membership reference from the board so a stale device cannot act on a new
membership. The first remaining member by insertion order is the administrator.
Codes are generated on request, returned once and stored only as SHA-256
digests. Leaving and direct Auth deletion remove the member's days, revoke an
outgoing administrator's invite and remove an empty group. The server uses Oslo
dates and prunes older dates for a member at their next successful share.

In an authorized **disposable nonproduction environment**, run `up.sql` as the
source role and POST `metadata.json` to the Hasura metadata endpoint. This is an
additive batch. Inspect consistency and the resulting roles after applying it.
The backup apply helper is scoped to backup tables. The metadata API accepts
only the four additions in this batch, and the existing Auth and backup metadata
must be preserved.

Use synthetic A and B in one group, C in a separate group and an anonymous
caller. Confirm A and B see each other's nicknames and scores, C sees its own
group, and anonymous read/write, forged actor/group input and attempted session
argument override fail. Check invite rotation, simultaneous attempts to take
the final slot, idempotent union, server-time date rejection, leave and direct
Auth deletion with a surviving member. Read back the manual backup permissions
and run the existing backup smoke for the synthetic accounts. Delete synthetic
members and verify the empty groups disappear. SQL and client tests alone do
not exercise the Hasura/JWT boundary.

For a reversible access rollback, remove the function permission and untrack
the function, then remove the response table permission and untrack the empty
response table. Keep the SQL schema and Auth deletion hooks in place for
existing memberships. Only a separately authorized data-removal operation
should drop tables containing records.

References: [Hasura custom SQL functions](https://hasura.io/docs/2.0/schema/postgres/custom-functions/)
and [Hasura Metadata API](https://hasura.io/docs/2.0/api-reference/metadata-api/index/).

## Guild weekly focus (S2) upgrade

**Status:** source only; `guild-focus-v1.sql` is not installed anywhere live.

One optional line (at most 120 code points, one line) for the current
Europe/Oslo calendar week, set, replaced or cleared (empty text) by the
administrator through the new `focus` operation of `guild_commons_v1`; every
current member reads it. The file is one transaction: it refuses any installed
function body other than S1's (`d51b6de2…`), adds `groups.focus_text` and
`groups.focus_week` with two checks, adds the helper
`oslo_week_start(timestamptz)` (Monday of the Oslo week; body `01ada650…`)
and replaces the `guild_commons_v1` body (new body `49fbc548…`). The
signature, return type, owner, grants and Hasura metadata are unchanged; do
not touch the metadata. Identity, membership checks, administrator authority
and the shared advisory lock are the S1 code paths.

Every `ok` result gains `focus: {text, weekStart}` **beside** `group`; `group`
keeps exactly its S1 keys. The released S1 client parses `group` strictly but
ignores other top-level fields, and the S2 client hides the focus when the
provider omits it, so either install order is safe. A focus stored for an
earlier week is never returned, and the Guild's next Commons call erases it.
A dormant Guild keeps its last line in storage until that call or Guild
deletion; the D6 cleanup job does not cover it. No history is kept.

Before applying: save `SELECT pg_get_functiondef('progresspal_social.guild_commons_v1(json,text,jsonb)'::regprocedure);`
for rollback, and confirm the inventory still matches
`guild-commons-inventory-expected.tsv`. Apply as the function owner with
"Track this" OFF. Afterwards the inventory differs only by the new function
body hash, the helper's function, ACL and owner rows, the two columns and the
two named checks (`groups_focus_text_length`, `groups_focus_week_set`, plus
PostgreSQL 18's named NOT NULL constraint for `focus_text`). Rollback reapplies the
saved definition; the two columns are then unused and stay until a separate
data decision. The PGlite probe above applies this upgrade on top of S1, so
every S1 assertion runs against the S2 body, and checks admin-only set and
clear, member read, handover, rollover, the Oslo DST weeks and the guard.

## Guild name upgrade

For an existing installation, compare the tracked `social_week` signature,
injected session argument and `user` permission with [metadata.json](metadata.json).
Save the current definition with
`SELECT pg_get_functiondef('progresspal_social.social_week(json,text,jsonb)'::regprocedure);`
and verify that the deployed definition matches the baseline in [up.sql](up.sql).
Apply [rename-guild.sql](rename-guild.sql) as the function owner, with tracking
disabled in the SQL console. For a fresh installation, apply the SQL files in
order, then apply the existing metadata batch. The upgrade replaces the
function body in a transaction and retains its identity and grants.
[PostgreSQL CREATE FUNCTION](https://www.postgresql.org/docs/current/sql-createfunction.html)

Using the synthetic accounts from the setup check, rename A's Guild through the
app and confirm B sees the new name. Verify that B, C with A's membership
reference, a stale membership and an anonymous caller cannot rename A's Guild.
Check that the active invite, members and shared dates survive the rename, and
that a surviving member can rename after taking over the administrator role.

The disposable PostgreSQL check can be run with
`node infra/nhost/social/probe-rename.mjs <pglite/dist/index.js>` and a local
PGlite distribution. It exercises the SQL before and after the upgrade.

To roll back the rename operation, reapply the saved function definition.
Names already saved remain on their existing groups. Recheck GraphQL access
and metadata consistency after either operation.

## Member invitation upgrade

On `progresspal-g0`, first inspect the installed function and the tracked
`user` mutation permission. Save the definition for rollback and check that
the source hash matches the value in [member-invites.sql](member-invites.sql).

```sql
SELECT pg_get_functiondef(oid) AS definition,
       encode(sha256(convert_to(replace(prosrc, E'\r\n', E'\n'), 'UTF8')), 'hex') AS source_hash
FROM pg_proc
WHERE oid = to_regprocedure('progresspal_social.social_week(json,text,jsonb)');
```

After authorization, apply only `member-invites.sql` as the function owner,
with tracking disabled in the SQL console. Its transaction rejects a missing
or unexpected function body. The legacy response field `canInvite` still
indicates the administrator. `canCreateInvite` grants code creation to members.
Every member can replace the active code. The administrator can deactivate it,
and any member can create a new code afterwards.

With existing synthetic accounts, rename as administrator and refresh as the
member. Check that the member's direct `rename` and `revoke` requests return
`not-admin`, then create a code as the member and verify the old code no longer
works. Deactivate as administrator and verify the member can create a fresh
code. Keep tokens and codes out of logs. The local probe above covers both
upgrades, stale memberships, outsiders, and the eight-member limit.
