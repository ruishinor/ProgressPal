# src/features/settings

The Settings surface shared by the Classic route (`/settings`) and the RPG route (`/rpg/settings`): profile, programme, local export / import / reset, and — on the unreleased Epic G branch only — the **remote backup card** ("Remote backup — Alpha") and the **email-link landing page** (`/cloud/callback`).

## Remote backup card (Epic G alpha, unreleased)

Scope: the smallest usable account, manual backup and manual restore UI over the already-reviewed `src/lib/cloud` and `src/lib/cloudBackup`, plus the smallest password-recovery journey through the existing account port. It is Settings only: no navigation entry, HUD, dashboard or onboarding control. It adds **no stylesheet byte** and no inline style (existing `Card`, `Button`, `FormField`, `TextInput`, `Select`, `Checkbox` and the `backup-preview`, `action-row`, `data-action__error` classes only); the CSS budget is unchanged.

### Rules

- **Labelled and disclosed.** The heading is `Remote backup — Alpha` in every state, and every state (off, unavailable, signed out, signed in) opens with the same three plain sentences: it is experimental; it is a manual backup, not automatic synchronization, and nothing is uploaded by opening Settings or signing in; the working data stays on this device; the cloud provider and the service operator can read uploaded backups; a file export is a separate way to keep a copy. No claim of encryption, privacy, protection, retention or legal standing (`cloudSettingsDisclosure.test.tsx`; a full privacy notice is G9).
- **Nothing runs by itself.** No request on mount, on navigation, on a timer or on focus. The only effects subscribe to the account's local state, move keyboard focus, or (on the callback page) complete the link once. Every cloud request is a button the learner pressed (`tests/architecture/cloudUi.test.ts`, `cloudSettingsAccount.test.tsx`, `cloudSettingsApp.test.tsx`, `e2e/cloud-settings.spec.ts`).
- **Off by default and silent.** While off, the card is the disclosure, one status sentence and one button; nothing reaches the network (`e2e/cloud-off-zero-traffic.spec.ts`).
- **No invented freshness.** The card never says or implies that the cloud copy is current, latest, newer, older, synced or up to date, and never compares it with this device. The only ordering shown is the server's stored time. `cloudModel.test.ts` scans every sentence for that vocabulary.
- **An unknown outcome is its own state.** It is never worded as stored and never as not stored, and offers **Check again** (the retained attempt is in memory only; there is no outbox or monitor).
- **Restore verifies before it offers and asks before it replaces.** Download and check writes nothing. When this device holds learner data the destructive warning is shown, an acknowledgement is required, and the existing local-file export is offered first; the last button is the only step that changes this device, through the existing atomic restore inside the app's local-mutation runner. It is unavailable while this tab cannot write locally (read-only, stale, another tab), while a local import or reset is running, and **while the learner's own local export is pending** (that export may still be reading the data the restore would replace; exporting is never consent by itself, and the handler refuses too). A failed verification leaves local data exactly as it was (`cloudRestoreExportRace.test.tsx`, `cloudSettingsExportRace.test.tsx`).
- **Forgot password? asks once and answers once.** Opening the reset view sends nothing; only Send reset link does. The answer is the same whether or not an account exists (a refusal that could reflect the account looks like success; only a failure about the request itself — cloud off, a limit, no connection — is reported), it does not repeat the address, and it says to open the link in this browser. The address is checked here with the account's own shape rule before anything is sent, so a malformed address is never reported as sent (`cloudPasswordRecovery.test.tsx`, and the equivalence test in `cloudPasswordRecoveryCallback.test.tsx`).
- **A reset link asks for the new password — and only a reset link.** After a successful reset exchange the callback page shows two password fields (`autocomplete="new-password"`) and one submit; the link alone is never reported as a change. Success is reported only after the provider acknowledged the change, and then only as "you were signed out on this device" (what the provider does with other sessions is a live-validation fact). A refusal is worded as a refusal (the form stays); a lost or unclear answer is worded as a doubt ("not confirmed"), never as success and never as "not changed"; an ended sign-in or cloud turned off closes the form. Neither password outlives the attempt, and nothing is rendered, logged, stored or put in the address.
- **Deliberately absent:** account deletion (G7), password change from inside Settings (only the recovery journey exists), synchronisation, automatic backup, dirty tracking, a status or history system (G8), privacy-policy text (G9), rollout controls (G10).

## Email-link landing page

`CloudCallbackPage` never reads the address. It asks `getCloudAccount().completeEmailLink()` (no argument) to handle the link: that reads the browser location once, removes every callback-shaped parameter, and only then exchanges the one-time code. The page renders outside both shells, once (a ref guards React's development double-run), shows nothing the link carried, writes nothing to the console, and every result ends at `/rpg/settings` (replacing its own history entry). A reset link that was really exchanged shows the new-password form on this same page; when the form ends, focus goes to the top of the page so the result is read first. Links that cannot be honoured (no record in this browser, expired, rejected, malformed) fail closed and, where a password may have been the point, say how to ask again. The provider-side redirect settings are the owner's step: `infra/nhost/README.md` ("Callback URLs"; password-reset emails use the same URL).

## Local-only wording (Epic G repair 01)

The released product is local-only and the default (cloud off) state still is, but a learner may now turn on an optional, manual remote backup. Learner-visible wording therefore avoids exclusivity ("only", "never", "no account", "Offline only", "stored remotely") and says what holds in **both** states: the working data is stored on this device, no account is needed, nothing is synchronized or uploaded automatically, backups are manual. The shell's mode label is `Local-first`. `tests/app/localFirstCopy.test.tsx` renders each affected surface with the remote backup off and on (including the Bokmål programme) and `tests/architecture/localFirstClaims.test.ts` keeps the retired phrases out of the source. Repository documents that describe the released build (`README.md`, `PRIVACY.md`, `SECURITY.md`, `docs/DEMO.md`) are not learner-visible in the app and are G9's to revise. The remaining mixed use of "cloud" and "remote" in button labels is also G9's.
