# Programvareutvikling source-to-platform fit report

Date: 2026-10-02. Branch: `maintenance/pre-e-hardening-source-fit`. Baseline: `95489ea0e08909054a4fa82120b28b131873d40c`.

This is an empirical fit analysis of the authored Programvareutvikling content against the live ProgressPal contracts. It registers nothing, authors no curriculum and changes no production programme. It does not validate the curriculum, the Bokmål, the learner experience or production readiness. Raw probe outputs and scripts are in the evidence package (`p2-*.json`, `p2-source-to-catalogue-mapping.csv`).

**Derived analysis, not authority.** This report interprets the protected Programme #2 authority (`00_CONTROL`, OD-P2-32, Package 21) and the live code. Where it disagrees with that authority, the authority stands. The first revision of this report (candidate C2) did disagree: it classified the static instructional-content layer as `PRE_E_DOMAIN_MODEL_REPLAN_REQUIRED` and future attempt/mastery persistence as `PRE_E_L3_SCOPE_DECISION_REQUIRED`, and it treated bundle size as a pre-emptive owner decision. Independent review found those conclusions wrong. Package 21 names the content layer and renderer as the first integration story (gap G06, delivery clauses DC-01…DC-08) and places persisted attempts, mastery and retrieval in a later step that needs its own schema decision (DC-37, DC-41, G14). This revision supersedes the C2 classification; section 5 states the corrected rows.

## 1. Verdict

- **The catalogue level fits.** `Programme → module → mission` maps to `Programme → Unit → Item` without distortion, with deterministic collision-free IDs, and needs no schema, ownership or backup-format change.
- **One bounded, source-justified platform adjustment was implemented and tested in Pre-E:** the additive shared vocabulary values `module` (unit type) and `lesson` (item type), so a module is not labelled "Week" and a lesson is not labelled "Lecture" or "Lab".
- **The static instructional content is Epic E scope, not a domain-model failure.** Lesson bodies, exercise prompts and canonical hints are static, bundled, programme-owned and non-persisted. They need a small optional content contract and a shared renderer. They need no schema change and do not disturb `Programme → Unit → Item`. A genuine domain-model stop remains available only if real Epic E implementation proves the hierarchy cannot represent the source without distortion.
- **Attempts, evaluators, mastery, retrieval and evidence-gated rewards are later phases** (`DEFERRED_FUTURE_PHASE_NOT_EPIC_E`). They will probably need a new store and migration, designed and RED-tested in that later phase. They are not blockers to Epic E and no schema is predeclared here. The normal stop rule stays: if Epic E itself unexpectedly needs schema v4, an ownership change, a backup-format change, cloud/auth or conflict semantics, or historical-state reinterpretation, it stops with exact evidence.
- **No C8 trigger is established.** Real P2 strings and counts sit inside ranges the shared UI already renders for CS50, and nothing has been rendered with P2 active. A generic shared lesson renderer is not by itself a C8 trigger.
- **Bundle size is a measured implementation constraint, not an advance decision.** The accepted budgets leave about 109 bytes of CSS gzip and about 100 kB of total JS gzip headroom (section 6). No budget change is authorized; Epic E builds the real slice, runs the existing check, and stops with exact measurements only if the real candidate breaches a budget.
- **The one genuine open owner decision is the visible shell brand** (OD-6).

## 6. Measured platform constraints

From `npm run check:bundle` on the Pre-E working tree (version `1.4.0`; the vocabulary change adds negligible bytes) and `p2-content-*.json`:

| Limit                 | Budget    | Current          | Headroom  |
| --------------------- | --------- | ---------------- | --------- |
| Largest JS chunk, raw | 500,000 B | 403,501 B (main) | 96,499 B  |
| Total JS, gzip        | 400,000 B | 299,912 B        | 100,088 B |
| Total CSS, gzip       | 12,000 B  | 11,891 B         | **109 B** |

| Content (M01+M02, minified)                             | Raw       | Gzip      |
| ------------------------------------------------------- | --------- | --------- |
| Lesson render subset (blocks, prompts, hints, feedback) | 369,645 B | 81,888 B  |
| Everything including evaluator payloads                 | 768,284 B | 130,842 B |

Expectations to test, not decisions to take: the render subset is about 82 kB gzip against about 100 kB of JS gzip headroom, but it is about 370 kB raw and would push the 403 kB main chunk past the 500 kB per-chunk limit, so it probably needs its own statically imported chunk. Any lesson-renderer CSS is large against 109 B of CSS gzip headroom, so reuse of existing styles matters. Evaluator payloads (the "everything" row) are a later-phase concern and are excluded from Epic E. Package 21 DC-08 and G15 prefer bounded per-mission or per-module loading, while the repository's offline service worker relies on install-time discovery of all boot assets and `AGENTS.md` forbids lazy route chunks. That tension is real, but its resolution depends on what the real Epic E build measures. These figures are estimates from the source, not a verdict.

Rule for Epic E: keep every accepted budget unchanged, build the real bounded slice, run `npm run check:bundle`, and inspect the actual chunking and incremental CSS and JS. Only a reproduced breach creates a decision gate, and then it stops with exact measurements and alternatives. No budget increase is authorized, and content weight alone is not a domain-model replan.

Real-string stress (`p2-vs-cs50-stress.json`): longest P2 item title 44 chars (CS50: 43), longest unit title 34 (CS50: 29), 13 items per unit (CS50 max: 22), max 170 minutes per item (CS50 max: 1,500). Size evidence is within already-rendered ranges; Norwegian wrapping at breakpoints and a longest-string check remain Epic E browser work.

## 7. The implemented adjustment

`module` is appended to `courseUnitTypeValues` and `lesson` to `courseItemTypeValues` (`src/lib/domain/constants.ts`), with the shared labels "Module" and "Lesson" (`src/features/course/model.ts`). Properties:

- **Append-only shared vocabulary.** Existing values keep their position and meaning; a test pins the frozen prefix. Stored rows, backups and XP `sourceType`s of existing programmes are unaffected, and old backups still parse.
- **No schema change.** The Dexie schema number, store shapes and index definitions are untouched. `type` is already an indexed string field on `course_units` and `course_items`; the new values are simply new index keys. The database name is unchanged.
- **No production programme uses them.** The registry still holds only CS50x.
- **Evidence** (`tests/programmes/moduleLessonVocabulary.test.ts`, 10 tests): append-only pin; schema acceptance and rejection of undeclared values; a synthetic module/lesson definition passing the real `validateProgrammeDefinition` (including a required-module rule that fails when absent); registration beside CS50 with CS50 still the explicit default; award identities `lesson_completed`/`module_completed` disjoint from CS50; real `evaluateProgressXp` awards for lesson completion and the module bonus; real `buildCourseMap` labels. With the two source files reverted, 9 of the 10 fail and the tenth (existing labels unchanged) passes, as intended (`control-module-lesson-red.txt`).
- **Forward compatibility, stated honestly.** An older application cannot parse a backup that contains a `module` or `lesson` row. That is the existing no-downgrade posture (C6) and cannot arise until a programme using them ships.

## 9. Owner decisions and gates

The C2 revision of this report listed seven owner decisions (D1 to D7). Independent review found that source and architecture already answer most of them. Only genuine choices remain.

**One open owner decision: the visible shell brand (OD-6).** The shell hard-codes "ProgressPal CS50 Edition" in `index.html` and `AppShell`. The owner's Phase I scope requires that no CS50 brand appear on Programvareutvikling-active surfaces and prefers making the title programme-aware through the existing terminology architecture. What visible string to show is the decision. Epic E builds the mechanism and its RED tests first, but must not claim a final Programvareutvikling-active browser candidate while the wrong brand is visible and the decision is absent.

**Conditional gates** fire only on reproduced in-scope evidence, not in advance:

- a concrete external link or asset becomes necessary: stop for that specific host and rights decision;
- the real build breaches an accepted bundle budget: stop with exact measurements and alternatives (section 6);
- real implementation proves `Programme → Unit → Item` cannot represent the source without distortion: domain-model stop;
- Epic E itself needs schema v4, an ownership change, a backup-format change, cloud/auth, new conflict semantics or historical-state reinterpretation: L3 stop;
- real rendering proves a reusable presentation abstraction is required (programme-specific forks, scattered programme-ID conditionals, a missing semantic asset boundary): C8 decision.
