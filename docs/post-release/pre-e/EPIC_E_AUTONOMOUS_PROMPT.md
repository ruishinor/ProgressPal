### 4.4 Runtime failure and timeout: one outcome, `evaluator_error`

The protected Package 21 DC-19 is current and is followed as written: an evaluator failure (runtime unavailable, **timeout in the app's runtime**, internal error) is reported as an app problem, must not count as an incorrect answer and must not create evidence either way. Until higher Programme #2 authority explicitly defines a learner-negative timeout, there is no such class in Epic E.

- **Runtime timeout.** Whatever caused it, including the runtime terminating code that exceeds the authored `timeout_s` (5 on all 42 `program` evaluators) or a resource limit, the outcome is `evaluator_error`: not learner-incorrect, no positive or negative mastery evidence, the learner is told the evaluation could not be completed, and a retry is allowed. The authored `timeout_s` is a limit the runtime enforces, not a rule that makes a timeout a learner result.
- **Other evaluator or infrastructure failure.** The runtime cannot initialize, the worker crashes, a WASM or runtime asset is unavailable or corrupt, the app-level watchdog expires, or the evaluator itself throws. Also `evaluator_error`, with the same consequences.
- **Persistence.** When the failure happens after a submit, the submitted answer is persisted as an immutable attempt with outcome `evaluator_error`, non-counting, and the retry is a new attempt (items 8 and 11; schema record section 3, invariant 7). A runtime known to be unavailable before submit creates no attempt (section 4.5).
- **Diagnosis does not decide the outcome.** The spike may show how a healthy runtime is told from an unhealthy one, for example by terminating a runaway execution and re-probing a fresh runtime with a known-good canary program. That diagnosis is for diagnostics, support and a future owner or authority decision. It does not turn a timeout into a learner result.
